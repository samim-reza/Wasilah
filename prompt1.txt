# Build a Production-Ready Quran Habit & Reading App

You are a senior mobile architect, product engineer, UI/UX designer, and backend engineer.

Build a **production-quality cross-platform Quran mobile application** inspired by the habit-forming UX principles of apps such as Duolingo, combined with the Quran reading capabilities users expect from Quran.com.

The goal is NOT to make a simple Quran reader.

The core product idea is:

> **Make reading at least one ayah of the Quran every day extremely easy, beautiful, and habit-forming.**

The application should encourage consistency through daily goals, streaks, intelligent reminders, personalized notifications, reading progress, and contextual prompts while remaining respectful and appropriate for a Quran application.

---

# 1. CORE PRODUCT PRINCIPLES

The application should be:

* Beautiful
* Calm
* Fast
* Minimal
* Reliable
* Modular
* Accessible
* Respectful of Islamic content
* Habit-oriented without making the Quran feel like a game
* Offline-friendly where practical
* Scalable to a large user base

The application must NOT feel like a generic CRUD application.

It should feel like a polished consumer mobile application.

---

Use the following stack unless there is a strong technical reason to change something.

## Web/Admin

Use Next.js only if an admin dashboard is required.

# 3. IMPORTANT ARCHITECTURAL REQUIREMENT

## DO NOT PUT THE ENTIRE APPLICATION IN A FEW FILES.

This is extremely important.

Do NOT create:

* one giant `App.tsx`
* one giant `api.ts`
* one giant `utils.ts`
* one giant notification file containing unrelated functionality
* one giant component containing the entire Quran reader
* one giant backend function containing every business rule

Every major feature must have its own module.

Code should be organized by **feature/domain**, not simply dumped into generic folders.

For example:

```text
src/
  features/
    auth/
    quran/
    reader/
    audio/
    bookmarks/
    notes/
    streak/
    goals/
    reminders/
    notifications/
    prayer/
    weather/
    search/
    profile/
    settings/
    onboarding/
```

Each feature should contain its own:

```text
components/
hooks/
services/
types/
utils/
screens/
```

where appropriate.

Keep related functionality together.

For example:

```text
features/notifications/
    components/
    hooks/
    services/
    types/
    utils/
```

The notification system must NOT be mixed into the Quran reader.

The reminder system must NOT be mixed into the notification UI.

Prayer-time calculations must NOT be mixed into weather logic.

API clients must NOT be mixed into UI components.

# 11. PAGINATION

Pagination must be implemented deliberately.

For API-based data:

```text
page
limit
offset/cursor
```

Use the API's native pagination mechanism when available.

For the Quran reader:

* Load only the required portion.
* Prefetch the next portion.
* Cache previously loaded content.
* Preserve scroll position.
* Avoid unnecessary network requests.

For search:

* Paginate search results.
* Debounce search input.
* Cancel stale requests where appropriate.

Do not fetch the entire Quran on every app launch.

When the network returns:


# 58. IMPORTANT CODING RULES

Follow these rules throughout the project.

### Rule 1

Do not create giant files.

If a file becomes unnecessarily large, split it.

### Rule 2

One module should have one clear responsibility.

### Rule 3

UI components should not contain business logic.

### Rule 4

Business logic should be testable without React.

### Rule 5

API calls should not be scattered through UI components.

### Rule 6

Notification delivery and reminder decisions must remain separate.

### Rule 7

Prayer calculations and weather calculations must remain separate.

### Rule 8

Audio must remain a separate feature.

### Rule 9

Streak calculations must be pure/testable.

### Rule 10

Use TypeScript strictly.

Avoid unnecessary `any`.

### Rule 11

Do not duplicate code.

Extract reusable utilities/components.

### Rule 12

Do not prematurely abstract every tiny function.

Use abstractions when there is a clear responsibility or reuse case.

### Rule 13

Do not install libraries unnecessarily.

Prefer the simplest reliable solution.

### Rule 14

Do not expose secrets.

### Rule 15

Do not fake API responses and pretend they are production-ready.

If an API requires configuration, clearly document the requirement.

# 59. CODE QUALITY STANDARD

Every production module should have:

* clear naming
* strict types
* error handling
* appropriate comments
* no dead code
* no unused imports
* no duplicated logic
* no magic numbers where configuration is appropriate

Comments should explain WHY, not simply WHAT.

Bad:

```ts
// Set notification time
```

Good:

```ts
// Schedule using the user's local timezone because daily reminders
// must remain stable when the device changes UTC offset.
```
